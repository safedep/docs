---
title: "Trust a Package After a False Positive"
sidebarTitle: "Trust a Package"
description: "Create a trust entry in the cloud policy to waive a malware, cooldown, vulnerability or license verdict for one package, with a reason and an expiry."
---

Use a trust entry when your team reviewed a package and decided that a verdict is wrong for your tenant. A trust entry waives the verdicts of its scopes for one package until it expires. It replaces [Malicious Package Exclusions](/governance/cloud/package-exclusions). PMG with the cloud policy ignores exclusions. The pull request check still applies them.

<Note>
  This guide needs the SafeDep Cloud Team or Enterprise plan and the Admin role. See [pricing](https://safedep.io/pricing).
</Note>

## Create the trust entry

```bash
safedep policy rule create --trust pkg:pypi/foo@1.0.3 --scope malware \
  --reason "False positive, S-88" --expires 30d --requested-by data-eng
```

- The selector names one package. Add a version in the PURL, or a range with `--vers`, to trust only some versions. A trust entry cannot use a prefix.
- `--scope` names the verdicts to waive. Give it more than once, or use `all`. See [Choose the scope](#choose-the-scope).
- `--expires` is required. It takes a duration, as `30d`, or a date, as `2027-01-26`. The expiry is at most 90 days from now.
- `--reason` is required.

The command warns that the rule loosens the policy, creates the rule and publishes a new policy revision. Every Owner and Admin of the tenant gets an email about it.

## Choose the scope

<Note>
  The scope `license` and the `--vulnerability` flag need a safedep CLI release later than v0.10.0.
</Note>

| Scope | Use it when | Where it applies |
|---|---|---|
| `malware` | SafeDep marks the package as malicious or suspicious, and you reviewed it | PMG and the pull request check |
| `cooldown` | You must install a new version before the dependency cooldown ends, such as your own SDK | PMG |
| `vulnerability` with `--vulnerability ID` | A pull request check fails on a vulnerability that you accept for this package, and you want the other vulnerabilities to still fail | The pull request check |
| `vulnerability` | A pull request check fails on the vulnerabilities of this package, and you accept every vulnerability of it, also one that SafeDep publishes later | The pull request check |
| `license` | A pull request check fails on the license of this package, and your team accepts the license | The pull request check |

Choose the narrowest scope. `--scope all` expands to the scopes that the CLI knows. In a safedep CLI release later than v0.10.0, these are `malware`, `cooldown`, `vulnerability` and `license`. A scope that a later release adds does not apply to this rule. `all` never names vulnerabilities.

A trust entry never waives a verdict of **verified** malware, whatever its scope. A trust entry also never skips the malware analysis. If a block entry selects the same package, the block entry wins.

PMG applies only the scopes `malware` and `cooldown`. It does not apply the scopes `vulnerability` and `license`, or a trust entry that names vulnerabilities.

## Waive named vulnerabilities

`--scope vulnerability` with one or more `--vulnerability` flags creates a trust entry that waives only the vulnerabilities that it names:

```bash
safedep policy rule create --trust pkg:npm/minimist@1.2.5 --scope vulnerability \
  --vulnerability CVE-2021-44906:vulnerable_code_not_in_execute_path \
  --reason "We never pass user input to minimist, S-91" --expires 30d
```

- Each value is `ID[:JUSTIFICATION]`. The id has its published form, as `CVE-2024-3094` or `GHSA-jfh8-c2jp-5v3q`. The pull request check also matches the aliases of a finding, so a CVE id waives the GHSA finding of the same vulnerability.
- The optional justification is one of the OpenVEX names `component_not_present`, `vulnerable_code_not_present`, `vulnerable_code_not_in_execute_path`, `vulnerable_code_cannot_be_controlled_by_adversary` or `inline_mitigations_already_exist`. Without it, `--reason` is the only explanation.
- A trust entry names at most 100 vulnerabilities. `--scope vulnerability` must be its only scope.
- `safedep policy rule list` and `safedep policy rule show` show the scope `named-vulnerability` with each id and its justification. To list these entries, run `safedep policy rule list --scope named-vulnerability`.

See [Waive one vulnerability of a package](/governance/cloud/policy/pull-request-checks#waive-one-vulnerability-of-a-package) for what each justification means.

## Extend or end the trust

To extend the trust entry, give a new expiry. A later expiry loosens the policy:

```bash
safedep policy rule update r_a41b7c9xkd --expires 90d --reason "Reviewed again for Q1"
```

To list the trust entries that expire soon:

```bash
safedep policy rule list --effect trust --expiring 7d
```

You cannot change the scopes or the vulnerability ids of a trust entry. To change them, delete the rule and create another.

To end the trust now, delete the rule. The delete tightens the policy:

```bash
safedep policy rule delete r_a41b7c9xkd --reason "Upstream fixed the false positive"
```

An expired trust entry no longer applies. PMG drops it at its expiry also when the endpoint is offline.

## Move from Malicious Package Exclusions

Trust entries with the scope `malware` replace Malicious Package Exclusions. SafeDep Cloud does not copy exclusions into the cloud policy. For each exclusion that you still need, create a trust entry:

| Exclusion field | Trust entry |
|---|---|
| Ecosystem, package name | The PURL, as `pkg:npm/name` |
| Version | A version in the PURL. For the version `0` (all versions), give no version. |
| Reason | `--reason` |
| Expires At | `--expires`. A trust entry needs an expiry of at most 90 days. |

PMG with `cloud.policy` on ignores the exclusions and applies only the trust entries. The pull request check still applies the exclusions.
