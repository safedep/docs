The pull request check of the [SafeDep GitHub App](/governance/integrations/github) and the [Bitbucket app](/governance/integrations/bitbucket-app) reads the cloud policy of your tenant. Both apps use the same check, so one policy applies to repositories on both forges. There is no separate setting in each app.

<Note>
  This guide needs the SafeDep Cloud Team or Enterprise plan and the Admin role. See [pricing](https://safedep.io/pricing). The app must scan the repositories for your tenant.
</Note>

## What the check reads

| Part of the policy | What the check does |
|---|---|
| `scan_gate.fail_on` | Fails on a vulnerability at or above this severity: `critical`, `high`, `medium`, `low` or `info`. |
| `scan_gate.fail_on_attacks` | With `report`, the check reports a malware verdict that is not verified and does not fail on it. With `fail`, the check also reports it and does not fail on it yet. |
| `scan_gate.licenses.deny` | Fails on a package whose license is on the list. |
| `scan_gate.licenses.allow` | With entries, fails on a package whose known license is not on the list. With no entries, the allow list is off. |
| `scan_gate.licenses.unknown` | What the check does with a package whose license is unknown: `allow`, `report` or `fail`. |
| Package rules | A block entry fails the check. A trust entry waives the findings of its scopes. |

For the SafeDep default of each setting and the scopes that the check applies, see [Cloud Policy Settings](/reference/cloud-policy-settings).

Verified malware always fails the check. No setting and no trust entry changes that. The check does not apply a dependency cooldown.

The check still applies the [Malicious Package Exclusions](/governance/cloud/package-exclusions) of your tenant. When an exclusion selects a package version, the check does not report an unverified malware verdict for that version. Verified malware still fails the check. PMG with `cloud.policy` on ignores exclusions.

`info` is a partial value: the vulnerability data has no info grade, so the check ranks a vulnerability with no severity as info.

## Fail on medium for a group of projects

1. Label the projects of the group. A repository is a project:

   ```bash
   safedep project label set acme/payments-api acme/ledger PAY/settlement --label custom/criticality=high
   ```

   If a repository has no project yet, see [Label projects](/governance/cloud/policy/target-a-group#label-projects).

2. Open the policy settings document and add a policy override:

   ```bash
   safedep policy edit -m "payments: fail on medium"
   ```

   ```yaml
   overrides:
     - name: payments
       priority: 200
       description: Stricter gate for payment services
       selector:
         matchLabels: {custom/criticality: high}
       spec:
         scan_gate:
           fail_on: medium
   ```

3. Preview the change. The preview counts the projects that the policy override reaches, and how many of them can enforce `medium`:

   ```bash
   safedep policy change show 18
   ```

4. Publish it:

   ```bash
   safedep policy change publish 18 -m "payments: fail on medium"
   ```

   Use the change number that `safedep policy edit` printed. The next check of each project uses the new revision.

To set the gate for every project of the tenant, set `scan_gate.fail_on` in the policy base instead. To target one forge, select on `scm/forge`, as in `matchLabels: {scm/forge: bitbucket}`.

## Deny a license

The check applies the deny list first, then the allow list, to the license of each package that the pull request adds or updates. For the match rules, see [License gate](/reference/cloud-policy-settings#license-gate).

<Note>
  The `safedep policy`, `safedep project label` and `safedep project policy` commands need a safedep CLI release later than v0.10.0. v0.10.0 does not have them.
</Note>

1. Open the policy settings document:

   ```bash
   safedep policy edit -m "Deny SSPL"
   ```

2. Set the deny list in the policy base. Your list replaces the default list, so copy the nine default ids and add the new one:

   ```yaml
   base:
     scan_gate:
       licenses:
         deny:
           licenses:
             - GPL-2.0
             - GPL-2.0-only
             - GPL-2.0-or-later
             - GPL-3.0
             - GPL-3.0-only
             - GPL-3.0-or-later
             - AGPL-3.0
             - AGPL-3.0-only
             - AGPL-3.0-or-later
             - SSPL-1.0
   ```

3. Preview and publish the change with `safedep policy change show` and `safedep policy change publish`, as in [Fail on medium for a group of projects](#fail-on-medium-for-a-group-of-projects).

If your list leaves out an id of the list below it (here, the default list), the change loosens the policy. The publish then asks for a confirmation, and every Owner and Admin of the tenant gets an email about it.

To deny no license for a group of projects, set `deny: {licenses: []}` in a policy override.

## Allow only some licenses

Set an allow list for a group of projects. A package with a known license that is not on the list fails the check:

```yaml
overrides:
  - name: distributed
    priority: 300
    description: Code that we ship to customers
    selector:
      matchLabels: {custom/distribution: external}
    spec:
      scan_gate:
        licenses:
          allow:
            licenses: [MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC]
```

- The deny list still applies. A license on both lists fails the check.
- A package with an unknown license still passes under `unknown: allow`. To allow only the listed licenses, also set `unknown: fail`. See [Fail on an unknown license](#fail-on-an-unknown-license).
- To turn off the allow list of the policy base for a group, set `allow: {licenses: []}` in a policy override.

For which change loosens the policy and which tightens it, see the [setting notes](/reference/cloud-policy-settings#policy-settings).

## Fail on an unknown license

Set `unknown` to `report` to show these packages in the check without a failure, or to `fail` to fail on them:

```yaml
base:
  scan_gate:
    licenses:
      unknown: report
```

<Warning>
  With `unknown: fail`, the check fails on each pull request that adds a package whose license SafeDep does not know. Start with `report`, and read the reported packages before you set `fail`.
</Warning>

## Waive a finding for one package

To pass a check that fails on a license or a vulnerability that your team accepts, create a trust entry. See [Waive license findings](/governance/cloud/policy/trust-a-package#waive-license-findings) and [Waive named vulnerabilities](/governance/cloud/policy/trust-a-package#waive-named-vulnerabilities).

## What the check shows

A failing check shows a policy block above the package report:

- On GitHub, in the comment of the SafeDep app and in the output of the check run.
- On Bitbucket, in the comment of the SafeDep app. The build status of the commit links to the pull request.

The block names the policy revision, each setting that the check read and the layer that set it, and each failing, waived and reported finding with the rule that decided it. This example comes from the SafeDep test data:

```markdown
**SafeDep policy: failed**

Policy: tenant revision 47 · SafeDep default policy revision 2

| Setting | Value | Set by | Coverage |
| --- | --- | --- | --- |
| `scan_gate.fail_on` | MEDIUM | policy override "payments" (selects `custom/criticality=high`) | ENFORCE |
| `scan_gate.licenses.deny` | GPL-2.0, GPL-2.0-only, GPL-2.0-or-later, GPL-3.0, GPL-3.0-only, GPL-3.0-or-later, AGPL-3.0, AGPL-3.0-only, AGPL-3.0-or-later | SafeDep default policy | ENFORCE |
| `scan_gate.licenses.allow` | off | no layer | ENFORCE |
| `scan_gate.licenses.unknown` | ALLOW | SafeDep default policy | ENFORCE |

| Package | Finding | Result | Rule |
| --- | --- | --- | --- |
| `left-padd 1.0.0` | block entry `r_9c1x4kq7dm` | Failing | "typosquat of left-pad" |
| `lodash 4.17.20` | 2 vulnerabilities (2 high): CVE-2020-8203, CVE-2021-23337 | Failing | `scan_gate.fail_on` |
| `minimist 1.2.5` | CVE-2021-44906 (critical) | Waived | trust entry `r_trust` (VULNERABILITY), expires 2026-12-03 |

Ask your security admin. They can run `safedep project policy show --project-id prj_payments`
```

For the text of each license finding, see [License findings](/reference/cloud-policy-settings#license-findings).

- A passing check shows no policy block.
- On a public repository, the block shows the rule id of a package rule, not its reason.
- When the tenant has no policy revision, the block names only the SafeDep default policy.

## When the check does not use your policy

- **The repository has no project.** The check resolves the policy with the `scm/` labels of the repository. The policy base, the package rules of the policy base and the policy overrides that select `scm/` labels apply. A `custom/` label needs a project. See [Label projects](/governance/cloud/policy/target-a-group#label-projects).
- **The installation is not linked to a tenant, or the plan of the tenant has no cloud policy.** The SafeDep default policy applies alone.
- **SafeDep Cloud cannot read the policy.** The check retries, and then fails with an error. It never falls back to the default policy, because the default policy can be looser than yours.

A failed check stops a merge only when the forge requires the check.
