---
title: Generate an AI BOM with vet
description: "Build an AI Bill of Materials from source code with vet's xBOM engine: AI SDK detections in CycloneDX with file and line evidence."
---

`vet` detects the AI libraries, SDKs, and agent frameworks your application actually calls. It analyzes source code and matches every call site against signatures for known AI SDKs. Each match is recorded with file and line evidence and written as an extended Bill of Materials (xBOM) into `vet`'s [CycloneDX](/concepts/sbom) output. The AI components in that document, each marked with an `ai` property, are your AI BOM. Because the inventory comes from call sites, it shows what the code calls, not just what the manifests declare.

Signature coverage tracks the AI ecosystem in current use. Providers include OpenAI, Anthropic, Google Gemini, xAI Grok, Mistral, Cohere, Groq, Ollama, AWS Bedrock, and Hugging Face. Frameworks and agent SDKs include LangChain, LangGraph, LlamaIndex, CrewAI, Vercel AI SDK, OpenAI Agents SDK, Claude Agent SDK, Pydantic AI, Spring AI, Semantic Kernel, and the Model Context Protocol (MCP) SDKs. The analyzer parses Python, JavaScript, TypeScript, Java, and Go. Coverage for each SDK follows the languages that the SDK supports. Browse the full signature set in the [vet repository](https://github.com/safedep/vet/tree/main/signatures). If your codebase uses an SDK that `vet` does not recognize, [write a custom signature](/governance/vet/ai-sdk-signatures).

AI is one category in the xBOM. The same scan also detects cryptographic operations, cloud integrations, and network, filesystem, and process capabilities. This guide covers the AI components; the full detection scope is documented in the [vet xBOM documentation](https://github.com/safedep/vet/blob/main/docs/xbom.md).

<Warning>
Code analysis in `vet` is experimental and may introduce breaking changes.
</Warning>

## Prerequisites

- `vet` [installed](/governance/vet/quickstart)
- Access to the source code you want to analyze

## Generate the AI BOM

<Steps>
  <Step title="Scan the source code">
    The first pass parses your source files, matches them against the embedded signatures, and stores the results in a local SQLite database. Point `--app` at your own code:

    ```bash
    vet code scan --db code.db --app ./src
    ```

    Skip test and generated code with `--exclude` (a regular expression), and restrict languages with `--lang` when you want a faster scan:

    ```bash
    vet code scan --db code.db \
      --app ./src \
      --lang python \
      --exclude ".*test.*" --exclude ".*__pycache__.*"
    ```
  </Step>

  <Step title="Write the CycloneDX BOM">
    The second pass runs a normal `vet` scan, enriches it with the recorded detections, and writes the BOM:

    ```bash
    vet scan -D ./src --code code.db --report-cdx xbom.json
    ```

    `xbom.json` is a standard CycloneDX document that carries the code-analysis detections alongside the declared packages. Every AI component in it has the `ai` property, so downstream tooling can filter on it.
  </Step>

  <Step title="Inspect detections directly (optional)">
    You can review what `vet` found without generating a BOM. Query the database for matches tagged `ai`:

    ```bash
    vet code query --db code.db --tag ai
    ```

    Narrow the results by language, vendor, or file path:

    ```bash
    vet code query --db code.db --tag ai --language python --limit 200
    vet code query --db code.db --vendor OpenAI
    vet code query --db code.db --file src/agents/
    ```
  </Step>
</Steps>

## Read the AI BOM

AI SDK calls detected in your code appear as standalone components with an `xbom:` bom-ref. The signature's vendor becomes the publisher, the `ai` property marks the component, and each occurrence records where the call sits in your source. This component records an Anthropic client constructed on line 3 of `src/app.py`:

```json
{
  "bom-ref": "xbom:anthropic.client",
  "type": "library",
  "name": "Anthropic API - AI client",
  "publisher": "Anthropic",
  "evidence": {
    "occurrences": [
      {
        "location": "src/app.py",
        "line": 3,
        "additionalContext": "anthropic//Anthropic"
      }
    ]
  },
  "properties": [
    { "name": "ai", "value": "true" }
  ]
}
```

`additionalContext` shows the matched call in the analyzer's namespace notation, with `//` separating the module path from the symbol. Detection follows calls, so an SDK that is imported but never called produces no component.

If you scan vendored dependency source through `--import-dir`, `vet` attempts to attach those detections to the corresponding declared package instead of a standalone component. This correlation is experimental and can miss; treat the `xbom:` components from your own code as the dependable output.

### Filter the AI components

The `ai` property makes the AI BOM easy to extract from the full document. With `jq`:

```bash
jq '.components[] | select(.properties[]? | .name == "ai" and .value == "true") | .name' xbom.json
```

<Note>
Two behaviors affect how you read results. Providers that applications reach through the OpenAI-compatible mode of the `openai` SDK (DeepSeek and Moonshot document this as their official path) appear as OpenAI usage, because the code calls the `openai` SDK. TypeScript needs no separate handling: JavaScript signatures cover it.
</Note>

## Run it in CI

Generate the BOM on each build and keep it as an artifact:

```yaml
- name: Build code analysis database
  run: vet code scan --app ./src --db code.db

- name: Generate xBOM with AI components
  run: vet scan -D ./src --code code.db --report-cdx xbom.json
```
