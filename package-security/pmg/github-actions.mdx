---
title: "PMG in GitHub Actions"
description: "Block malicious packages in GitHub Actions CI with one PMG action step, a job summary, and kernel enforcement."
---

[PMG](https://github.com/safedep/pmg) runs as a persistent proxy in CI/CD. The `safedep/pmg` action starts it once per job. The proxy intercepts installs from every [supported package manager](https://github.com/safedep/pmg#supported-package-managers) and blocks each package flagged as malicious. At the end of the job, the action stops the proxy, writes a job summary, and fails the job when PMG blocked a package.

<Note>
  In CI, PMG is non-interactive: flagged packages are always blocked, never prompted. For local development use the wrapped commands (`pmg npm install`) covered in the [PMG quickstart](/package-security/pmg/quickstart).
</Note>

## Use the SafeDep PMG action

Add one `safedep/pmg` step right after `actions/checkout`. The job needs no other PMG step.

```yaml
- uses: actions/checkout@v6

- uses: safedep/pmg@v0.34.0
  with:
    api-key: ${{ secrets.SAFEDEP_API_KEY }}
    tenant-id: ${{ secrets.SAFEDEP_TENANT_ID }}

- run: npm ci   # intercepted automatically
```

Put the action before the language setup steps, so the proxy sees the traffic of every later step. Use one `safedep/pmg` step per job. A second step fails, and the proxy of the first step keeps running.

By default, the action runs the proxy in server mode. On a GitHub hosted runner, it also turns on [kernel enforcement](#enforce-in-the-kernel). Set `timeout-minutes` on the job. A proxy that stops serving holds the job until the timeout.

PMG blocks malicious packages using SafeDep's free community intelligence with or without credentials. Add the optional `api-key` and `tenant-id` to connect the run to [SafeDep Cloud](/governance/cloud/overview), so block events sync to [Endpoint Hub](/governance/cloud/endpoint-hub/overview) before the runner is destroyed.

<Note>
  Use `safedep/pmg@v0.34.0` or a later release tag. The post step, the job summary, and the `fail-on-violation`, `auto-stop` and `baseline` inputs need v0.34.0 and a runner that runs Node 24 actions. A self-hosted runner needs runner version 2.327.1 or later. The `v1` tag points at an older action without these inputs. GitHub warns about an unknown input and runs the job without it.
</Note>

### Upgrade from v0.33.0 or earlier

Earlier releases needed a `pmg proxy stop --fail-on-violation` step at the end of the job. From v0.34.0, the post step of the action does this work. Remove the stop step. Server mode is the default, so the job no longer needs `server-mode: true`.

A job that keeps its own stop step must set `auto-stop: false`. Otherwise the post step finds no proxy and fails the job, because a stop step could hide a block.

## What happens at the end of the job

The action has a post step. GitHub runs it at the end of the job, also when an earlier step fails and when the job is cancelled. The post step:

1. Stops the proxy. With `api-key`, the proxy sends its last events to SafeDep Cloud.
2. Proposes a network profile from the hosts that the job reached. See [Allow Only Known Hosts in GitHub Actions](/package-security/pmg/github-actions-network-policy).
3. Writes the job summary. The summary shows the verdict, the number of blocked packages, each denied connection, and each destination host. The run also gets an annotation when PMG blocked a package, and one for each denial.
4. Fails the job when PMG blocked a package or the network policy denied a connection.

These inputs change the post step:

| Input | Default | Effect |
| --- | --- | --- |
| `fail-on-violation` | `true` | Set `false` to report a block without a failed job. When PMG cannot stop the proxy, for example after a crash, the job fails with every setting. |
| `auto-stop` | `true` | Set `false` when a step of the job stops the proxy. |
| `baseline` | `true` | Set `false` to leave the proposed profile and the list of destination hosts out of the summary. |

<Warning>
  On a public repository, anyone can read the job summary. It lists the hosts that the job reached. Set `baseline: false` to leave them out. A denied connection still shows in the summary, with its host.
</Warning>

## Example workflow

A full workflow that installs dependencies through PMG on every pull request:

```yaml install-dependencies.yml expandable
name: Install Dependencies
on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  install-deps:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v6

      # Start PMG. The post step stops it and fails the job on a block.
      - uses: safedep/pmg@v0.34.0
        with:
          api-key: ${{ secrets.SAFEDEP_API_KEY }}
          tenant-id: ${{ secrets.SAFEDEP_TENANT_ID }}

      # Your usual language setup and install
      - uses: actions/setup-node@v6
        with:
          node-version: "24"

      - run: npm ci
```

## See blocks from every pipeline

With the `api-key` and `tenant-id` inputs, the blocks from every job go to one tenant. To review them across all repositories, see [Review Package Blocks Across CI Pipelines](/governance/cloud/endpoint-hub/ci-package-blocks).

<Note>
  This needs the SafeDep Cloud Team or Enterprise plan. See [pricing](https://safedep.io/pricing).
</Note>

Proxy variables are a request that a process can ignore. A step that runs `env -i`, uses `sudo`, or calls an HTTP client of its own bypasses the proxy. Kernel enforcement makes the Linux kernel route every process on the runner through PMG.

The `enforce` input is `auto` by default. The action enforces when the job runs on a GitHub hosted runner, on the runner host, with passwordless `sudo`. GitHub hosted Ubuntu runners meet these conditions. In a job container, on a self-hosted runner, or without `sudo`, the action runs the proxy without enforcement and says so in the log.

Set `enforce: true` to fail the job where the runner cannot enforce. Set `enforce: false` to turn enforcement off.

```yaml
- uses: safedep/pmg@v0.34.0
  with:
    enforce: true
    enforce-namespaces: redirect
    api-key: ${{ secrets.SAFEDEP_API_KEY }}
    tenant-id: ${{ secrets.SAFEDEP_TENANT_ID }}

- run: npm ci
```

`enforce-namespaces: redirect` also routes the containers that steps start, such as `docker run` and `docker build`. See [Protect Docker builds and containers](#protect-docker-builds-and-containers).

The action installs the PMG CA into the system trust store, starts the proxy as root, and exports the trust variables. The post step stops the root proxy. A step that runs `pmg` as root uses the `PMG_BIN` and `PMG_PROXY_STATE` variables that the action exports:

```yaml
- run: sudo "$PMG_BIN" proxy status --state "$PMG_PROXY_STATE"
```

The runner is not exempt. Its connections to GitHub go through the proxy, which passes them through with the real certificate. If the proxy stops serving but keeps running, the runner cannot report. GitHub then cancels the job after its `timeout-minutes`, and the post step does not run. The GitHub default is 360 minutes, so set a shorter timeout on every job.

The `enforce-ports`, `enforce-exempt-users`, `enforce-exempt-executables`, `enforce-skip-destinations`, and `enforce-namespaces` inputs set the policy without a config file. Each list adds to the config's list. With `enforce: auto`, an `enforce-*` input fails the job where the action cannot enforce, so a runner change does not turn enforcement off without notice. See the [action reference](https://github.com/safedep/pmg/blob/main/docs/github-action.md#kernel-enforcement) for the input table, and [Kernel Enforcement on Linux](/package-security/pmg/kernel-enforcement) for the policy keys and what enforcement does not cover.

To refuse every host that the job does not need, add a network policy. See [Allow Only Known Hosts in GitHub Actions](/package-security/pmg/github-actions-network-policy).

### Protect Docker builds and containers

With `enforce-namespaces: redirect`, PMG also checks the packages that a container installs. This includes the `RUN` steps of `docker build`, `docker run`, and Docker actions.

PMG reads the registry traffic with its own CA. A container that does not trust this CA fails the TLS handshake. The action exports the path of a CA bundle as `PMG_CA_BUNDLE`. The bundle holds the PMG CA and the public root CAs, so the other hosts still work. Give this file to each container that installs packages.

For a build, pass the bundle as a build secret. The secret is not stored in the image.

```yaml docker-build.yml expandable
name: Build Docker Image
on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v6

      - uses: safedep/pmg@v0.34.0
        with:
          enforce: true
          enforce-namespaces: redirect

      - uses: docker/setup-buildx-action@v4

      - uses: docker/build-push-action@v7
        with:
          context: .
          push: false
          tags: app:ci
          secret-files: pmg-ca=${{ env.PMG_CA_BUNDLE }}
```

Without `docker/build-push-action`, pass the same secret to the Docker CLI:

```bash
docker build --secret id=pmg-ca,src=$PMG_CA_BUNDLE -t app:ci .
```

In the Dockerfile, mount the secret in each `RUN` step that installs packages:

```dockerfile Dockerfile
FROM node:24-slim
WORKDIR /app
COPY package.json package-lock.json ./

# The bundle is present only when the build gets the pmg-ca secret.
# A build without the secret, such as a local build, uses the CAs of the image.
RUN --mount=type=secret,id=pmg-ca,target=/run/secrets/pmg-ca.pem,mode=0444 \
    if [ -f /run/secrets/pmg-ca.pem ]; then export NODE_EXTRA_CA_CERTS=/run/secrets/pmg-ca.pem; fi; \
    npm ci

COPY . .
CMD ["node", "index.js"]
```

`mode=0444` is required. BuildKit mounts a secret that only root can read, and the install can run as a different user.

Set the variable that your package manager reads:

| Package manager | Variable |
| --- | --- |
| npm, pnpm | `NODE_EXTRA_CA_CERTS` |
| pip | `PIP_CERT` |
| uv, Go | `SSL_CERT_FILE` |
| Cargo | `CARGO_HTTP_CAINFO` |

To give the bundle to a container at runtime, mount it in the container:

<Tabs>
  <Tab title="docker run">
    ```bash
    docker run -v "$PWD":/app -w /app \
      -v "$PMG_CA_BUNDLE":/pmg-ca.pem:ro -e NODE_EXTRA_CA_CERTS=/pmg-ca.pem \
      node:24 npm ci
    ```
  </Tab>
  <Tab title="Docker action">
    A Docker action can read files in the workspace, at `/github/workspace`. Copy the bundle there in a step before the action:

    ```yaml
    - run: cp "$PMG_CA_BUNDLE" pmg-ca.pem
    - uses: some/docker-action@v1
      env:
        NODE_EXTRA_CA_CERTS: /github/workspace/pmg-ca.pem
    ```
  </Tab>
</Tabs>

## Job containers and Docker actions

<Note>
  You need this setup only when the job runs in a job container. Kernel enforcement does not work in a job container. On a job without a job container, use `enforce-namespaces: redirect` instead. It sends Docker actions, `docker://` steps, `docker run`, and `docker build` through PMG. See [Protect Docker builds and containers](#protect-docker-builds-and-containers).
</Note>

In a job with a job container (`jobs.<job_id>.container`), the action and the proxy run inside that container, and `run:` steps reach the proxy at `127.0.0.1`. A Docker action or a `docker://` step runs in a different container on the job network, where `127.0.0.1` is its own loopback, so its connection to the proxy fails. Set `expose-to-job-network` to bind the proxy to the job container's address on the job network:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    container:
      image: node:24
      options: --init
    steps:
      - uses: actions/checkout@v6
      - uses: safedep/pmg@v0.34.0
        with:
          expose-to-job-network: true
      - run: npm ci
      - uses: docker://node:24
        with:
          args: npm ci
```

Every container on the job network can then reach the proxy, including service containers. The runner mounts `/github/home` in the job container and in Docker actions, so the exported CA path is valid in both. The action fails when the job has no job container, and it warns when `HOME`, `XDG_CONFIG_HOME`, or `PMG_CONFIG_DIR` moves the CA outside `/github/home`.

The action needs a POSIX shell and common tools in the image, such as busybox, plus `curl` or `wget`. It does not need `bash` or Node in the image. Alpine images such as `node:24-alpine` work as they are. An Alpine job container on arm64 does not work, because the runner has no Node build for it.

## Self-hosted runners

`enforce: auto` does not enforce on a self-hosted runner. Kernel enforcement adds the PMG CA to the trust store of the host, and the CA stays after the job. A host that more than one repository shares then trusts the PMG CA for every job. Set `enforce: true` on an ephemeral runner, or on a host that only trusted jobs use.

A host can also run the proxy as a `systemd` service for every job. Set `enforce: false` on the action, because the host proxy already enforces. See [Kernel Enforcement on Linux](/package-security/pmg/kernel-enforcement).

## Use raw commands

To wire the proxy up directly without the action:

```yaml
- run: pmg proxy start --daemon
- run: pmg proxy env >> "$GITHUB_ENV"
- run: npm ci
- run: pmg proxy stop --fail-on-violation
  if: always()
```

<Warning>
  `pmg proxy env >> "$GITHUB_ENV"` sets `HTTP_PROXY`, `HTTPS_PROXY`, and the CA variables for every later step. `pmg proxy stop` does not remove the variables. A step after the stop step that uses the network connects to the stopped proxy and fails, for example `actions/upload-artifact` with `ECONNRESET`. Put the stop step last in the job. The action does not have this problem, because its post step empties the proxy variables after the stop.
</Warning>

For the proxy lifecycle, certificate trust, bind address, and cloud event sync, see the [persistent proxy server docs](https://github.com/safedep/pmg/blob/main/docs/persistent-proxy.md).
